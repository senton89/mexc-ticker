# mexc-ticker

Сборщик рыночных данных MEXC: сделки по списку символов → минутные свечи OHLCV → PostgreSQL → REST.
Учебный проект на Go (сентябрь 2026), написан за один день с фокусом на корректный
конкурентный пайплайн и graceful shutdown без потери данных.

**Стек:** Go 1.25, стандартная библиотека (`net/http`, `log/slog`, `context`), `pgx/v5`,
`x/sync/errgroup`, PostgreSQL 16, Docker (multi-stage → distroless, образ 21 МБ), GitHub Actions.

## Быстрый старт

```bash
docker compose up --build -d          # postgres + app; миграция применяется при первом старте
curl -s localhost:8080/healthz        # {"status":"ok"}
curl -s 'localhost:8080/candles?symbol=BTCUSDT' | jq   # свечи за последний час
```

Локально без Docker: `make db-up`, `cp .env.example .env`, `env $(cat .env) make run`.
Проверки: `make lint` (golangci-lint v2), `make test` (`go test -race`), `make build`.

## API

| Метод | Путь | Параметры | Ответ |
|---|---|---|---|
| GET | `/healthz` | — | `200 {"status":"ok"}` или `503` если БД недоступна (ping с таймаутом 2 с) |
| GET | `/candles` | `symbol` (обяз.), `from`, `to` — RFC3339, по умолчанию последний час, макс. диапазон 7 дней | `200 [ {symbol, start (UTC), open, high, low, close, volume} ]`, `400` при ошибке параметров |

## Конфигурация (env)

`SYMBOLS` (≤30, через запятую), `DATABASE_URL`, `HTTP_ADDR` (`:8080`), `BATCH_SIZE` (100),
`FLUSH_INTERVAL` (5s), `POLL_INTERVAL` (2s), `MEXC_BASE_URL`. Конфиг валидируется при старте:
пустой список символов, >30 символов или `SYMBOLS/POLL_INTERVAL > 10 rps` — сервис не запустится.

## Архитектура

```
cmd/collector          wiring: config → store → source → agg → http; errgroup; signal.NotifyContext
internal/config        env → Config с валидацией
internal/model         Trade, Candle — общие типы, чтобы пакеты не зависели друг от друга
internal/source        MEXC REST /api/v3/trades: горутина на символ, дедупликация, → chan Trade
internal/agg           один воркер, map[symbol]*Candle: закрытие по границе минуты или по тикеру
internal/store         pgx: батч upsert (ON CONFLICT DO UPDATE), QueryCandles [from, to)
internal/api           ServeMux 1.22 (GET /candles, GET /healthz), slog-middleware
migrations/001_init.sql candles(symbol, ts, o, h, l, c, volume, PK(symbol, ts))
```

Поток данных: `source.Run` → `chan Trade` (буфер 1024) → `agg.Run` → `chan Candle` (256) → `store.Run`.
Граф импортов направленный: `model ← source, agg, store, api ← main`. `api` зависит от интерфейса
`CandleReader`, объявленного у потребителя, — HTTP-слой не знает про pgx.

### Цепочка остановки (graceful shutdown)

SIGINT/SIGTERM → `signal.NotifyContext` отменяет ctx → `source` выходит из циклов и **закрывает**
`chan Trade` → `agg` читает до закрытия, дописывает все открытые свечи в `chan Candle` и закрывает
его → `store` флашит остаток буфера на `context.WithoutCancel` с таймаутом 5 с → `http.Server.Shutdown`
→ `errgroup.Wait` → закрытие пула. Отмена входит через голову пайплайна, дальше распространяется
закрытием каналов — поэтому ни одна свеча из памяти не теряется. В Docker остановка занимает <1 с
(`stop_grace_period: 15s` — запас на медленную БД).

## Почему REST, а не WebSocket

Изначально планировался канал `spot@public.deals.v3.api@SYMBOL`. Эксперимент показал две вещи:
(1) MEXC перевёл deals-каналы на protobuf (`...v3.api.pb@100ms@...`); (2) подписки с моего IP
возвращают `Reason: Blocked!` при живом соединении и рабочем PING/PONG — региональная блокировка
маркет-данных. REST `GET /api/v3/trades` доступен, публичен, без ключа. Контракт
`source.Run(ctx, out chan<- Trade) error` не зависит от транспорта: замена на WebSocket не трогает
`agg`, `store`, `api`.

## Решения и компромиссы

**pgx напрямую, а не GORM.** Одна таблица, два запроса. ORM добавил бы слой абстракции, скрыл
`ON CONFLICT` и батчинг за нестандартными вызовами и ничего не дал взамен. pgx v5 — нативный
протокол PostgreSQL, `pgx.Batch` отправляет N upsert'ов одним round-trip'ом, `float64 ↔ numeric`
кодируется без дополнительных типов.

**Падение между флешами.** Буфер `store` живёт в памяти до `BATCH_SIZE` строк или `FLUSH_INTERVAL`
(5 с); при `kill -9` эти свечи теряются, при SIGTERM — дописываются. После рестарта первый опрос
забирает до 500 последних сделок, поэтому последние минуты частично восстанавливаются, а upsert
делает повторную запись идемпотентной (last write wins, объём не суммируется). Полная гарантия —
WAL/ack-механизм источника, чего у REST-поллинга нет.

**Канал, а не Kafka.** Один процесс, один продюсер, один консьюмер. Брокер добавил бы сетевой хоп,
сериализацию и отдельный компонент для эксплуатации, не дав ничего сверх буферизованного канала.
Точка врезки, если появится второй потребитель свечей (алертинг, другой сервис), — между `agg` и
`store`: там канал заменяется на продюсер.

**Дедупликация без `id`.** MEXC возвращает `id: null`, а несколько сделок в одну миллисекунду —
норма (один тейкер против нескольких мейкеров). Состояние на символ: `lastTime` + множество
отпечатков `price|qty|tradeType` только за последнюю миллисекунду. Локально в горутине символа —
без мьютексов.

**Горутина на символ в `source`, один воркер в `agg`.** В `source` у каждого символа собственный
I/O и собственное состояние дедупа — независимые горутины естественны. В `agg` все сделки уже идут
через один канал, единственный читатель работает с `map` без синхронизации; фан-аут дал бы только
мьютексы.

**Закрытие свечи по двум событиям.** Основное — пришла сделка следующей минуты. Резервное — тикер
раз в секунду закрывает свечи старше `Start + 1m + 5s grace` (символ замолчал). Grace нужен, потому
что поллинг с интервалом 2 с приносит сделку 12:00:59.9 только в 12:01:01–02.

**`NUMERIC` в БД, `float64` в Go.** Деньги в БД — точный тип. В Go `float64` ради скорости
разработки; накопление ошибки в `volume` при суммировании тысяч сделок — известный минус, лечится
`shopspring/decimal`.

**`pgx.Batch`, а не `CopyFrom`.** `COPY` не умеет `ON CONFLICT`: нужна временная таблица и вторая
команда. При ≤30 свечей в минуту батч из upsert'ов проще и достаточен; порог перехода на
COPY+temp — тысячи строк на флеш.

**Масштабирование на 1000 символов.** Первым ломается лимит MEXC: 30 подписок на соединение,
~300 weight/10 с на IP — REST-поллинг 1000 символов невозможен, нужен WebSocket (≥34 соединений)
или несколько инстансов с шардированием по символам. Второе — агрегатор: 1000 записей в `map` и
пробег тикера раз в секунду ещё дёшевы, но поздние сделки после закрытия по тикеру потребуют
`lastClosed` по символу и upsert хвоста вместо дропа. Третье — `store`: 1000 upsert'ов в минуту
переживёт `Batch`, но при флеше каждые 5 с батч из ~80 строк уже стоит перевести на COPY.
БД — партиционирование `candles` по дням и ретеншн.

## Известные ограничения

- Первые свечи после старта могут быть неполными: первый опрос забирает историю (≤500 сделок).
- Две сделки с одинаковыми `time`, `price`, `qty`, `tradeType` схлопываются в одну (нет `id`).
- Сделка, пришедшая после закрытия свечи тикером, дропается с `WARN`, а не досчитывается.
- При ошибке флеша буфер сбрасывается (память ограничена); retry с backoff не реализован.
- `429` от MEXC не обрабатывается отдельно (`Retry-After`) — при лимите увеличивайте `POLL_INTERVAL`.
- Тесты покрывают только чистую логику агрегации (`apply`, табличный тест); `source`, `store`, `api`
  проверены вручную и через живой прогон, автотестов нет.
- Нет `/metrics`.
